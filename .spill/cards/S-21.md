## Purpose
The gap analysis left one early question open: does a DOM canvas stay fast with a few hundred artboards? Nothing has measured it. Paper files grow large, and agents write many screens quickly, so the editor needs targets and a test that holds them.

## Requirements
1. A generated stress file (a script in the repo) with 300 artboards of realistic content: text, nested flex frames, images and SVG, about 30,000 layers in all.
2. Targets on that file, on the development machine: opening and first paint under 3 s; panning and zooming at 50 fps or better (measured frame times); selecting and dragging a layer without dropped frames beyond 2 in a 2 s drag; typing in a text layer with input-to-paint under 32 ms; a single `update_styles` from an agent painted within 100 ms.
3. Artboards far outside the viewport skip rendering work (for example with `content-visibility` or by not mounting their content), without changing what measurement-based tools return for the page in view.
4. Panels stay responsive: the layers panel renders only the rows in view; the pages and comments lists do the same past a few hundred rows.
5. A performance test runs the measurements and records the numbers, so regressions show up as failed checks.

## Out of scope
Multiplayer scale, files over 100,000 layers, GPU canvas rendering.

## Acceptance checks
- The stress file opens with first paint under 3 s.
- Pan and zoom on it measure 50 fps or better.
- Dragging a layer drops at most 2 frames over 2 s; typing paints within 32 ms.
- An agent `update_styles` paints within 100 ms, and `get_node_info` sizes for the page in view are unchanged with off-screen skipping on.
- The layers panel with all 30,000 layers expanded scrolls without visible lag (frame times under 20 ms).
